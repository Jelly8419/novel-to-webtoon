# 기능 개발 루프

작업: $ARGUMENTS

아래 순서를 지킨다. 각 단계가 끝나면 한 줄로 진행 상황을 알린다.

## 1. 작업 파악

- 노션 "작업 일정"(`docs/notion.md`)에서 이 작업을 찾아 내용과 메모를 읽고, 상태를 "진행 중"으로 바꾼다. 인자가 비어 있으면 상태가 "할 일"인 작업 중 가장 앞 주차의 것을 제안하고 확인받는다.
- `CLAUDE.md`, 관련 `docs/` 문서, `docs/decisions/` 를 확인한다. 결정과 충돌하면 멈추고 묻는다.

## 2. 계획 (승인 받기 전 코드 수정 금지)

다음을 짧게 제시하고 사용자 승인을 기다린다.

- 바꿀 파일과 이유
- 접근 방식 (대안이 있으면 1줄 비교)
- 테스트 계획: 어떤 동작을 무엇으로 검증할지
- 실제 AI API 호출 필요 여부 (기본은 mock)

## 3. 구현

- `feat/<짧은-영문-이름>` 브랜치를 만든다.
- 계획 범위만 수정한다. 범위 밖 개선점은 마지막에 목록으로만 남긴다.
- 저장할 때마다 훅이 포맷·린트를 돌린다. 린트 오류가 보고되면 바로 고친다.

## 4. 테스트

- 새 로직에는 `*.test.ts` 를 함께 작성한다. 버그 수정은 실패하는 테스트부터 쓴다.
- `npm run check` 를 통과시킨다.
- 화면 변경이면 `npm run dev` 로 띄우고 Playwright MCP로 해당 화면을 열어 직접 확인한다.

## 5. 리뷰

- `reviewer` 서브에이전트에게 변경 사항(`git diff main...HEAD`) 검토를 맡긴다.
- 지적 중 버그·보안·규칙 위반은 고치고, 취향 문제는 사용자에게 판단을 넘긴다.

## 6. 커밋과 PR

- 의미 단위로 커밋한다 (`feat:`, `fix:`, `test:` …, 한국어 본문).
- 푸시와 PR 생성은 사용자 확인 후 진행한다. PR 본문: 무엇을 왜, 테스트 방법, 스크린샷(화면 변경 시), 남은 일.

## 7. 기록

- 노션 작업 상태를 "완료"로 바꾸고 메모에 PR 링크를 남긴다.
- 작업 중 방향을 바꾼 결정이 있었다면 `/decision`, 오래 막혔던 문제가 있었다면 `/troubleshoot` 로 기록할지 사용자에게 묻는다.
